## Context

See proposal.md - Why. Relevant existing state:

- `@amiceli/vitest-cucumber` (`^4.7.0`) is already a devDependency of `client-games` (added by phase 02, `dungeon-tactics-gherkin-runner`), and is what every step-definition file uses to load and run `.feature` files under Vitest.
- **Discovered during implementation — its public API cannot be used from a standalone script.** `loadFeature()` (and everything else exported from the package's single entry point, `dist/src/module.js`) only works when actually executing inside a live Vitest worker. Confirmed by direct reproduction: running a script that imports `loadFeature` via `tsx`, via `node`, and via `vite-node` all fail — either on module resolution (the package's compiled output uses extensionless relative imports, which only bundler-style resolvers like Vite/Vitest tolerate, not Node's native ESM loader) or, once that's routed around, on a hard runtime error (`Vitest failed to access its internal state`) because the bundled module graph calls into `vitest`'s `expect`/worker-state machinery at import time. A throwaway probe test confirmed `loadFeature()` works fine *when the file is collected and run by the actual Vitest test runner* — which is exactly how the phase 02 step-definition file already uses it — but that path requires the generator to run as a Vitest-collected test file, which would either (a) need its own dedicated Vitest config to keep it out of the default `npm test` sweep (more moving parts than this "small script" warrants), or (b) live under `client-games/src/**/*.test.ts` and therefore run on every `npm test` invocation, silently turning it into the pre-test hook this change's proposal explicitly deferred. Neither is a good fit.
- Given that, this change does **not** depend on `@amiceli/vitest-cucumber` at all — see the corrected Decisions section below. The library remains a devDependency for phase 02's own purpose; this change just doesn't add to that usage.
- Gherkin step-list grammar guarantees the first step in any Background or Scenario is always a concrete `Given`/`When`/`Then` — an `And`/`But` never appears first. That means a single running "last concrete keyword," scanned top-to-bottom through a whole file, resolves every `And`/`But` correctly without needing to track feature/rule/scenario/background boundaries as distinct step lists.
- Phase 02 is implemented (commit `92fa2cc`): `client-games/src/games/dungeon-tactics-solo/features/` contains `melee-attack.feature` + `melee-attack.feature.test.ts` + `README.md`. The example scenario includes a `Given`/`And`/`When`/`Then` sequence, exercising the `And`-resolution logic directly during verification.

## Goals / Non-Goals

**Goals:**
- Produce a correct, deterministic, mechanically-derived catalog from whatever `.feature` files exist at generation time.
- Correctly resolve `And`/`But` steps to their effective Given/When/Then keyword, since the catalog's value depends on grouping by real semantic meaning, not literal keyword text.
- Keep the script a plain dev-time Node/tsx script with no runtime footprint in the shipped client bundle, and no dependency on a Vitest worker being alive.

**Non-Goals:**
- A Markdown rendering of the catalog (the phase doc calls this a "cheap optional add-on"; not needed for the harness repo's phase 06 consumer, which reads JSON — deferred).
- A pre-test hook or CI staleness check (deferred per proposal — manual/on-demand is the v1 default).
- Any change to how `.feature` files are authored or organized (that's phase 02's and phase 08's concern).
- Deduplicating step text that differs only cosmetically (e.g. trailing whitespace, punctuation) beyond exact string match after trimming — semantic/fuzzy matching is out of scope.

## Decisions

### Use a small line-based step extractor, not `loadFeature()` — reversing the originally-planned decision
The original plan (see git history on this file) was to reuse `@amiceli/vitest-cucumber`'s `loadFeature()`, on the reasoning that it avoids duplicating parsing logic and can't disagree with the real execution parser on edge cases. That's no longer viable: as documented in Context above, the package's only public entry point requires a live Vitest worker and cannot run from a standalone script by any reasonably-robust means (deep-importing its unexported internal files was the one thing that technically worked in a spike, but relies on file paths with no semver contract — a version bump could silently break the catalog generator with no warning). The phase doc itself pre-approved a fallback for exactly this situation: "a lightweight Gherkin parser is enough."
Decision: extract step lines directly with a regex (`/^(Given|When|Then|And|But)\s+(.+)$/`) applied to each trimmed line of the raw `.feature` file text, skipping doc-string block bodies (delimited by `"""` or `` ``` ``) so their content isn't misparsed as steps. This only needs to solve a much narrower problem than full Gherkin parsing — extracting keyword + step text — so the "might disagree with the real parser" risk from the original reasoning doesn't meaningfully apply: there's no scenario/rule/outline/example-substitution logic to get subtly wrong, just line matching. Scope explicitly excludes non-English Gherkin (`@amiceli/vitest-cucumber` supports other spoken languages via its `SpokenParser`; nothing in this repo's `.feature` files uses them today) — out of scope, not silently mishandled: a non-English keyword line simply won't match `STEP_LINE` and won't be miscategorized, it'll just be skipped.

### Resolve `And`/`But` via a single running "last concrete keyword" scanned through the whole file
Per the Context note on Gherkin grammar, a step list (Background or Scenario) always opens with a concrete Given/When/Then, so tracking one `lastKeyword` variable top-to-bottom through the file — without separately walking Background/Scenario/Rule boundaries as an AST would — produces the same correct result with much less code. When a line's keyword is `And`/`But`, file its text under `lastKeyword`; when it's `Given`/`When`/`Then`, update `lastKeyword` and file under itself. If an `And`/`But` line is ever encountered with no `lastKeyword` yet set (a malformed `.feature` file), throw rather than silently mis-bucketing.
Alternative considered: catalog `And`/`But` steps under their own literal keyword. Rejected — it would silently produce a catalog where two textually-adjacent steps like `Given a unit\nAnd it has 10 HP` show up under unrelated buckets ("Given" and "And"), which is useless for the harness repo's vocabulary-reuse check (phase 04's whole purpose).

### Deduplicate by (effective keyword, trimmed step text) after full traversal
Collect all `(keyword, details)` pairs across every file first, then dedupe via a `Map` keyed on `` `${keyword}::${details.trim()}` ``, before building the final grouped JSON. This is simpler and less error-prone than deduplicating per-file or streaming, and the catalog is small (bounded by however many `.feature` files exist) so building it fully in memory is not a performance concern.

### Output shape: `{ given: string[], when: string[], then: string[] }`, each list sorted
Lowercase-keyed, alphabetically-sorted arrays keep the JSON diff-friendly across regenerations (the proposal's stated reason for choosing JSON) — an unsorted list would reorder on every regeneration based on file-walk order, producing noisy diffs unrelated to actual content changes. Sorting is the cheapest way to make the output stable without tracking file/scenario provenance, which nothing downstream needs yet.
Alternative considered: preserve file/scenario provenance per step (e.g. `{ text, sourceFile, sourceScenario }`). Rejected for v1 — the proposal's stated consumer (harness phase 06) only needs "does this text already exist," not where; provenance can be added later as a non-breaking additive field if a real need appears.

### Script location and invocation: `client-games/scripts/generate-step-catalog.ts` run via `tsx`
Matches the phase doc's suggested path. `client-games` has no existing `scripts/` directory or script-running convention of its own (its `package.json` `scripts` block only has `dev`/`build`/`preview`), but the repo root already uses `tsx` for `npm run dev` (see root CLAUDE.md: "Development (backend only — tsx watch)"), so reusing `tsx <path>` for a one-off dev script is consistent with an existing project pattern rather than introducing a new one. Add `"generate:step-catalog": "tsx scripts/generate-step-catalog.ts"` to `client-games/package.json`'s `scripts` block.

## Risks / Trade-offs

- **[Risk]** A hand-rolled regex extractor could drift from real Gherkin syntax the execution parser (`@amiceli/vitest-cucumber`) accepts — e.g. tags, `Scenario Outline`/`Examples` tables, or non-English keywords — producing a catalog that's silently incomplete rather than erroring. → **Mitigation:** scope is deliberately narrow (see Decisions) and the extractor only needs to recognize step lines, not validate full Gherkin structure; a step line that doesn't match `STEP_LINE` is simply skipped, not miscategorized. If richer `.feature` syntax (rules, outlines) is added later and the catalog looks wrong, this is the first place to revisit.
- **[Risk]** The `And`/`But` resolution logic is the one piece of real logic in an otherwise mechanical script; getting the single running "last keyword" wrong would silently mis-bucket steps without erroring. → **Mitigation:** the spec's "Catalog reflects the existing example scenario" requirement is exactly the regression check for this — `melee-attack.feature`'s existing `And` step (`An NPC with 3 hp at column 6, row 5`, which must resolve to `given`) exercises this path directly, and was verified to do so during implementation.
- **[Risk]** Doc-string bodies containing a line that happens to start with a Gherkin keyword (e.g. `Given` appearing inside prose in a doc string) could be misparsed as a step if the `"""`/`` ``` `` toggle logic has a bug. → **Mitigation:** none of the current `.feature` files use doc strings, so this path isn't exercised yet; add a doc-string test case if/when a scenario introduces one.

## Migration Plan

No runtime migration (dev-tooling only, no deployed service or data model). No sequencing dependency remains: phase 02 is implemented, so this change's tasks (script, npm script, and end-to-end verification against the real `melee-attack.feature`) can all proceed without waiting on other work.
